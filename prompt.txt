  A.9 Rewrite processProject to include record migration + ack gate

  Extend the existing transaction wrap. Pseudocode (plan §7):
  
  public function processProject(int $projectId, array $rules, int $migrationId): array
  {
      $status = $this->getProjectStatus($migrationId, $projectId);
      if ($status === self::PROJECT_COMPLETED || $status === self::PROJECT_SKIPPED) {
          return ['status' => self::PROJECT_SKIPPED, 'changes' => 0, 'error' => ''];
      }
      if ($status === self::PROJECT_NEEDS_ACK) {
          return ['status' => self::PROJECT_BLOCKED, 'changes' => 0,
                  'error' => 'Warnings unacknowledged'];
      }
      if ($status !== self::PROJECT_IN_PROGRESS) {
          $this->markProjectStatus($migrationId, $projectId, self::PROJECT_IN_PROGRESS);
      }

      try {
          $this->module->query('START TRANSACTION', []);
  
          $plan = $this->planFieldChanges($projectId, $rules);

          $changes = [];
          $changes = array_merge($changes, $this->updateProjectSiteSubset($projectId, $rules));
          $changes = array_merge($changes, $this->updateValueMapping($projectId, $rules, $plan));
          $changes = array_merge($changes, $this->applyFieldChanges($projectId, $plan));

          $shardName = $plan['field_name']
              ? $this->validateDataTableName($this->getProjectDataTable($projectId))
              : null;

          $totalRows = 0;
          $newCodesAllocated = $plan['code_allocations'];

          foreach ($plan['record_migrations'] as $rm) {
              $rows = $this->updateRecordValues(
                  $projectId, $plan['field_name'], (string)$rm['old_code'], (string)$rm['new_code']
              );
              $totalRows += $rows;
              $changes[] = [
                  'rule_id'     => $rm['rule_id'] ?? null,
                  'change_type' => self::CHANGE_RECORD_VALUE_MIGRATION,
                  'field_name'  => $plan['field_name'],
                  'old_value'   => (string)$rm['old_code'],
                  'new_value'   => (string)$rm['new_code'],
                  'details'     => json_encode([
                      'rows_affected' => $rows,
                      'data_table'    => $shardName,
                      'reason'        => $rm['reason'] ?? null,
                  ]),
              ];
          }
  
          $this->logToEntity($projectId, $migrationId, $changes);
          $this->module->query('COMMIT', []);

          $this->logToREDCap($projectId, $changes);
          $this->markProjectStatus($migrationId, $projectId, self::PROJECT_COMPLETED, count($changes));

          return [
              'status'              => self::PROJECT_COMPLETED,
              'changes'             => count($changes),
              'newCodesAllocated'   => array_map(fn($a) => ['code' => $a['new_code'], 'site' => $a['new_site']], $newCodesAllocated),
              'recordsMigrated'     => $totalRows,
              'error'               => '',
          ];
      } catch (\Throwable $e) {
          try { $this->module->query('ROLLBACK', []); } catch (\Throwable $_) {}
          $this->module->emError("Site migration project $projectId failed: " . $e->getMessage());
          $this->markProjectStatus($migrationId, $projectId, self::PROJECT_FAILED, 0, $e->getMessage());
          return ['status' => self::PROJECT_FAILED, 'changes' => 0, 'error' => $e->getMessage()];
      }
  }

  The whole transaction must cover both redcap_metadata and redcap_data* writes — verify your DB engine is InnoDB; MyISAM kills rollback.

  Acceptance criteria

  - A rename rule applied to a project leaves redcap_data* untouched, changes only element_enum (one code's label changes), and adds one value_mapping entry.
  Re-running is a no-op.
  - A merge rule with three old sites on a project on redcap_data3:
    - Adds a new code to element_enum (verify max-existing + 1).
    - Suffixes the three old codes' labels with (retired — migrated to <NewSite>).
    - Issues UPDATE redcap_data3 statements that move all records from the three old codes to the new code.
    - Logs one code_allocation, three field_label, three record_value_migration entries (each with details.rows_affected and details.data_table = "redcap_data3").
    - Adds one new value_mapping entry pointing the new site to the new code.
    - Re-running is a no-op (zero rows touched, zero log entries).
  - A project with branching logic [site] = '1' referencing a soon-to-be-rewritten code:
    - Appears in preview with codeReferences.branching_logic >= 1 and status='needs_ack'.
    - Is excluded from the pending list in startSiteMigration and included in blocked.
    - The references modal lists the row with a snippet.
    - Clicking Acknowledge flips status to pending and the next run loop picks it up.
  - A simulated mid-processProject exception (throw after the data-table update) leaves the project's element_enum, value_mapping, project_subset, AND
  redcap_data*.value all in their pre-migration state.
  - Crons (onCoreProtocolsScanCron et al.) early-exit when migration-in-progress is true.
  - The REDCap audit log (logEvent) shows one entry per migrated project with a multi-line description matching plan §12.
  - Sunset-without-target leaves records untouched and only suffixes the label.
  - A second rule set targeting the same projects skips already-completed projects without re-running plans against them.

  Watchouts / pitfalls

  - Per-project code numbering — each project has its own element_enum. Project A's "Main Hospital" might be code 24, Project B's might be 51. value_mapping is
  per-project too, so this is fine. Never assume codes are stable across projects.
  - Pull + push mapping — both branches in redcap-oncore-fields-mapping need the new entry. Easy to forget the push side.
  - Codes can be non-numeric — element_enum allows alphanumeric codes. parseElementEnum should treat them as strings, not ints. allocateNewCode should compute max+1
  only when all codes are numeric; otherwise allocate the smallest unused positive integer.
  - oc values with quotes / brackets — site names like Quarry Rd clinics;Hoover Pavilion and Psychiatry: Page Mill, Porter Dr, other contain characters that look like
  enum delimiters. Use proper parsing: split on | (space-pipe-space), then split the first ,  only.
  - mysqli affected_rows — check how the existing query() wrapper surfaces this. If it doesn't, count rows BEFORE the UPDATE and use that as the reported count.
  - getDataTable availability — framework v5+. The existing getProjectDataTable already handles the fallback. Don't rebuild that.
  - Don't log code references inside the transaction — the scan ran during preview; persist in code_references_json then. Live execution just reads it. Re-running the
  scan during processProject is wasted work.
  - Library setting update runs ONCE, not per project — updateLibrarySettings(rules, libraryIndex) is called by startMigration, not by processProject. Make sure rev-3
  doesn't accidentally move it into the per-project loop.
  - REGEXP escaping — preg_quote for PCRE; for MySQL REGEXP you need to escape ] and \ differently. Test the pattern in MySQL directly.

  Out of scope

  - Auto-rewriting branching logic / alerts when codes change (plan §4.8 explicitly rejects this).
  - Cross-library moves (plan §4.2).
  - Backfilling (changed to X) suffixes left by old rev-2 runs (no production runs yet).
  - An "undo" tool (mentioned as future work in §4.9).
