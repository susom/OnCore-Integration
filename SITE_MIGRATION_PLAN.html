Design Decisions

Key Constraints & Choices

DecisionChoiceRationale
Migrate redcap_dataNoCoded values stay intact. Historical data never touched.
Forward-compat with OnCore syncvalue_mapping dual entriesBoth old and new OnCore site name strings map to the same REDCap coded value.
Researcher visibilityLabel suffix"Old Site (changed to New Site)" — full traceability, no data loss.
Execution granularityPer-project atomic transactionA failure in project N never affects projects 1…N-1.
Cron safetyDisable all 4 sync cronsSystem-level flag checked at start of each cron method.
IdempotencySkip-if-migrated checkRule sets can be re-run safely; already-completed projects are skipped.
Live progressClient-driven AJAX pollingOne project per call — no PHP timeout risk. Client polls every ~1.5 s.
Audit trailEntity log + REDCap::logEventResearch team sees changes in Project Logging. Internal log for admin tooling.
Data Model

What Actually Changes

Study site names live in five independent storage locations. redcap_data is never written.

📚
System Settings — Library Site List
Key: library-oncore-study-sites sub_settings inside each library. Loaded once per protocol context. Updated once at migration start, not per-project.
System-wide
📋
Project Setting — Site Subset
Key: redcap-oncore-project-site-studies. JSON array of site name strings per project. Drives which sites appear in the field mapping UI.
Per-project
🗺️
Project Setting — Field Value Mapping
Key: redcap-oncore-fields-mapping. JSON with {"oc":"Site Name","rc":"coded_value"} entries. New entries added for new site names; old entries kept for backward compatibility.
Per-project
🏷️
REDCap Metadata — Field Option Labels
Table: redcap_metadata.element_enum. Pipe-delimited option strings. Old site labels suffixed with "(changed to X)" or "(merged into X)". Direct parameterized SQL UPDATE — no REDCap::getData round-trip.
Per-project
🚫
redcap_data — Patient Records
Coded values (e.g. "1", "2") remain exactly as stored. No writes. Historical data integrity is preserved.
Untouched

Why no entity table updates? The redcap_entity_oncore_subjects entity stores person-level demographics (MRN, name, DOB) — it has no studySites column. Study site is a protocol-subject-level concept that flows through the value mapping into a REDCap field. Updating the mapping is sufficient.

Decisions Needed

Open Questions

Needs Answer

Merge — Primary Code Selection

When "Site X" (rc="1") and "Site Y" (rc="2") merge into "Site Z", future OnCore syncs must map "Site Z" to exactly one existing REDCap coded value.

  • Option A — Admin picks via dropdown in rule editor (recommended)
  • Option B — Always default to first listed old site's code
  • Option C — Create a new dropdown option in REDCap instrument
Needs Answer

Number of Libraries

Study sites are scoped to libraries (sub_settings). Each linked project uses one library index.

If one library → rule editor is simple, no selector needed.
If multiple libraries → rule editor needs a library dropdown to know which site list to show.

How many libraries are configured in your system?

Decided

System Site List — Replace vs. Append

Old site name entries are replaced in the library (assumes OnCore has already been updated). Both old and new `oc` keys are kept in value_mapping for backward compat with any cached/historical API responses.

Decided

redcap_data — No Migration

REDCap coded values (e.g. "1", "2") are never written. The label suffix approach gives researchers full traceability. Future OnCore syncs use value_mapping dual entries to resolve both old and new site names.
