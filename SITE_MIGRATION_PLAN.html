Data Model

What Actually Changes

Study site names live in five independent storage locations. redcap_data is never written.

📚
System Settings — Library Site List
Key: library-oncore-study-sites sub_settings inside each library. Loaded once per protocol context. Updated once at migration start, not per-project.
System-wide
📋
Project Setting — Site Subset
Key: redcap-oncore-project-site-studies. JSON array of site name strings per project. Drives which sites appear in the field mapping UI.
Per-project
🗺️
Project Setting — Field Value Mapping
Key: redcap-oncore-fields-mapping. JSON with {"oc":"Site Name","rc":"coded_value"} entries. New entries added for new site names; old entries kept for backward compatibility.
Per-project
🏷️
REDCap Metadata — Field Option Labels
Table: redcap_metadata.element_enum. Pipe-delimited option strings. Old site labels suffixed with "(changed to X)" or "(merged into X)". Direct parameterized SQL UPDATE — no REDCap::getData round-trip.
Per-project
🚫
redcap_data, redcap_data2, … redcap_data8 — Patient Records (sharded)
Coded values (e.g. "1", "2") remain exactly as stored across all eight shards. No writes anywhere. The optional deep-preview path issues read-only COUNT(*) on the project's specific shard via $module->getDataTable($pid) — never against a hard-coded table name. Historical data integrity is preserved.
Untouched (× 8)

Why no entity table updates? The redcap_entity_oncore_subjects entity stores person-level demographics (MRN, name, DOB) — it has no studySites column. Study site is a protocol-subject-level concept that flows through the value mapping into a REDCap field. Updating the mapping is sufficient.

Sharding rule for this module: redcap_metadata is a single table (no shard) — safe to UPDATE ... WHERE project_id = ?. redcap_data* and redcap_log_event* are sharded — never hard-code the table name. Use $module->getDataTable($pid) for data reads and REDCap::logEvent() for log writes. See Sharded Data Tables for the full reference.

Decisions (Answered)

Decision Points — Answered by May 2026 Worksheet

The original plan left four open questions. The Stanford worksheet provides concrete answers for all of them.

Decided

Merge — Primary Code Selection

Admin picks via dropdown in the rule editor (Option A). The worksheet defines an unambiguous default: the row marked "Rename" in each merge group is the primary; all rows marked "Move to Line N" or "Sunset" merge into it.

Worksheet examples: Main Hospital → primary = SCI-Palo Alto; Children's Hospital → SCI-LPCH; Redwood City → SHC Redwood City; Emeryville → SCI-Emeryville.

Decided

Number of Libraries

For the May 2026 migration: single library (Stanford). The UI still surfaces a library selector when more than one is configured, but the seed rule set targets one library.

Out of scope: two worksheet rows (SCI-South Bay, SCI-Emeryville) require an OnCore-side library move from SCI → Stanford. That step is done manually in OnCore before/in parallel with this migration. The EM does not move sites between libraries.

Decided

System Site List — Replace

Old site name entries are replaced in library-oncore-study-sites. Both old and new oc keys are retained in the per-project value_mapping for backward compat with any in-flight OnCore payload during the cutover window.

Sunset rows: e.g. SHC - Emeryville retired 2025-09-04 — removed from library, old oc entry retained, no new oc entry added (OnCore will not emit again).

Decided

redcap_data* — No Migration (× 8 shards)

REDCap coded values (e.g. "1", "2") are never written in any of the eight redcap_data* shards. The label suffix approach gives researchers full traceability. Future OnCore syncs use value_mapping dual entries.

Shard-aware reads only: the optional Deep Preview path uses $module->getDataTable($pid) to pick the project's shard for read-only COUNT queries — never hard-coded.

REDCap Architecture

Sharded Data Tables — Reference

REDCap shards record data horizontally across up to eight physical tables. Each project is assigned to exactly one shard, recorded in redcap_projects.data_table. The same scheme applies to redcap_log_event*. This migration's design is shard-safe: every write targets a non-sharded table or goes through a sharding-aware API.

Table familySharded?Resolved viaTouched by this migration?
redcap_data, redcap_data2, … redcap_data8Yes (8 shards)$module->getDataTable($pid) (framework v5+) · fallback SELECT data_table FROM redcap_projectsNo writes · optional read-only COUNT in Deep Preview
redcap_log_event, redcap_log_event2, …YesREDCap::logEvent() — auto-routes to correct shardYes — via the API (never raw SQL)
redcap_metadataNo (single table)Direct WHERE project_id = ?Yes — UPDATE element_enum
redcap_projectsNoDirectNo · read-only lookup for shard fallback
redcap_external_modules_settingsNoEM settings APIsYes — via setProjectSetting / setSystemSetting
redcap_entity_oncore_* (this EM)NoDirect (one table per entity type)Yes — 3 new entity types

Hard rule for SiteMigration.php: never hard-code the literal string "redcap_data" in any SQL emitted by this class. Always go through getDataTable($pid). The only place the literal table name appears is in the optional Deep Preview helper countRecordsWithSiteCode(), and even there it's the return value of getDataTable(), not a string literal.

Why this matters: hard-coding redcap_data would silently miss every project that lives on shards 2 through 6 — a class of bug that would compile, pass linting, and produce wrong results without any error. The Deep Preview path is the only read path that touches a data shard, so this is the only place the rule applies in code today; the convention exists to head off the same mistake in any future enhancement.
